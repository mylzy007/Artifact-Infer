# Lit-check: D1-I4 — Wire-byte budget runtime controller (B*, m*)

## Idea recap
Two-variable closed-loop controller: byte-budget `B*` (latency target) + router-margin floor `m*` (quality guard). Selects (drop policy, drop rate, optional quant) per layer-step from a discrete table.

## Keywords searched
- MoE adaptive token drop rate online controller runtime 2024-2025
- "byte budget controller" LLM serving
- Capacity-aware MoE inference / SLO MoE

## Top candidates considered (all verified)
1. **Capacity-Aware Inference** (He et al., ICLR 2026, arXiv:2503.05066, verified=YES via D1 trace) — runtime token drop & reroute driven by *straggler* signal; not byte budget.
2. **SMIDT** (AAAI-26, ojs.aaai.org/.../39403, verified=YES via D2 trace) — dynamic Top-K with prefill/decode disaggregation; per-request not per-step.
3. **BrownoutServe** (Hu et al., 2025, arXiv:2507.17133, verified=YES via D3 trace) — SLO-aware MoE serving under bursty workload with "dynamic brownout" token handling; closest in spirit to controller-level adaptation.
4. **AdaMoE** (arXiv:2406.13233, verified=YES this trace) — token-adaptive routing via null experts; *training* mechanism, not runtime controller.
5. **NeurIPS'24 Toward Efficient Inference for MoE** (verified=YES via D1 trace) — characterization, no controller.
6. **Tutel** (Hwang et al., arXiv:2206.03382, verified=YES via D1 trace) — adaptive parallelism; not byte budget at policy layer.

## Closest 3 priors + differences
- **BrownoutServe** — closest semantic neighbor: SLO + bursty + brownout token control. **Diff**: D1-I4 uses *worst-peer bytes* as control variable + *router-margin floor* as quality guard; brownout abstract doesn't isolate byte budget. **Needs deep read** to confirm.
- **Capacity-Aware Inference** — runtime adaptive drop, but trigger is straggler not byte-budget. **Diff**: control objective.
- **SMIDT** — dynamic Top-K with phase awareness. **Diff**: K rather than drop rate; per-request not per-layer-step.

## Has been published? **partial**
Runtime adaptive drop policies exist (Capacity-Aware, BrownoutServe, SMIDT). The specific "byte budget + router margin" dual-variable controller using D1-I10 worst-peer-bytes metric is not directly published.

## Collision rating: **接近但有差异**
BrownoutServe is the #1 risk and *requires deep read* before any pilot. SMIDT and Capacity-Aware are adjacent on the "runtime adaptive MoE knob" theme but use different signals.

## Novelty space remaining
- *Worst-peer wire bytes* as the controlled variable (D1-I10 product)
- *Router margin floor* as quality guard (vs straggler / latency / capacity signals)
- Discrete lookup table (not RL/MPC) → simple actuator

## Conclusion: **需调整**
Must deep-read BrownoutServe (arXiv:2507.17133) before any pilot to confirm differentiation. If confirmed: positionable as "the controller that operationalizes D1-I10 byte cost". If BrownoutServe already covers byte-budget control: D1-I4 collapses to a special case.
