# Lit-check: D3-I1 — Request-class router with offline-binned MoE policy lookup

## Idea recap
Offline regressor predicts L_recv envelope from (prompt_len, max_tokens, sampling); bin requests into K classes; each class gets pre-computed (drop policy, r, K_eff) bundle.

## Keywords searched
- workload-adaptive MoE inference (D3 trace)
- request shape predictor MoE policy
- prompt length / max_tokens classifier for serving

## Top candidates (all verified)
1. **LYNX** (arXiv:2411.08982, verified=YES via D3 trace) — workload-adaptive MoE serving (title) but mechanism is AffinityBinning intra-batch.
2. **SMIDT** (AAAI'26) — dynamic Top-K with prefill/decode disaggregation; instance-level.
3. **DuoServe-MoE** (arXiv:2509.07379) — dual-phase MoE prefetch+cache scheduling.
4. **BrownoutServe** (arXiv:2507.17133) — SLO-aware MoE serving under bursty workload.
5. **MoE-Lens** (arXiv:2504.09345) — resource-aware scheduler with phase distinction.

## Closest 3 priors + differences
- **LYNX** — title overlap but mechanism is intra-batch token remapping, not request-class binning. **Diff**: D3-I1 is per-request offline lookup.
- **BrownoutServe** — SLO + bursty; needs deep read on whether it includes request-class binning. Adjacent.
- **SMIDT** — per-phase disaggregated K. **Diff**: D3-I1 is per-class policy bundle, not just K.

## Has been published? **partial**
Per-request workload classification for LLM serving is established (e.g., output-length predictor work in D3-I7). MoE-specific policy class binning is not directly published.

## Collision rating: **接近但有差异**
The lookup-table aspect is heuristic; the MoE-specific class structure is the differentiator.

## Conclusion: **需调整**
Reframe as baseline-only or as D3-I2's offline counterpart. Standalone weak.
