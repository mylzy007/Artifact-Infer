# 本周主要工作

## 1. SVD 谱：dispatch 端激活不天然低秩（NO-GO）

在 6 个 MoE 层、32K lcc token 上算累计方差解释率：

| layer | EV @ d/4 | EV @ d/2 |
|---:|---:|---:|
| 2 | 0.82 | 0.93 |
| 12 | **0.66** | 0.85 |
| 24 | **0.67** | 0.85 |
| 36 | 0.70 | 0.86 |
| 46 | 0.78 | 0.90 |

中层最难，按 ≥0.90@d/4 判据所有层都不通过。试了**按域分（lcc/code 比 dureader/中文 高 0.15）**但中层无救。

## 2. 进一步验证 dispatch 端死透

- **多层全模型 SVD sweep**：把 SVD 同时装到所有 48 层，2× 压缩 → PPL +119%，4× → +711%，**直接 cliff**
- **Routing-aware projection**：专门设计的投影器强制保住路由 logits（数学上 100% 一致），但**反而更差**（2× PPL +863%）
- **诊断**：根因不在路由，**在 residual stream 上的 L² 误差跨 48 层乘性累积**。任何线性映射都救不了。
- **Task-aware 训练 P_down/P_up**：只训 2M 参数想反超 SVD，结果训练炸（**MoE 路由 top-k 不可微，损失景观不连续**）

**结论**：dispatch 端方向结构性 NO-GO，跟具体映射方法无关。

## 3. 转向 combine 端，连击 4 个 win

| 实验 | 关键发现 |
|---|---|
| Combine top-magnitude sparsify sweep | **2× 压缩 PPL 只涨 3.3%**（同档 dispatch SVD 涨 119%）—— 第一个正面结果 |
| Error feedback 变种对比 | **topk_l2**（保 L2 norm 的缩放）winner，比 naive 强 20–156pp；L1 和 stochastic 反而炸 |
| 跨域验证 | topk_l2 在 lcc/QA/中文/英文报告 4 域上**都赢 naive**；4× PPL +14–25% |
| **+ FP8 叠加** | **FP8 在已稀疏的值上 round-trip 几乎免费**：4× sparse + 2× FP8 = 8× 总，PPL +17.2%（vs 单 4× sparse 的 +18.0%） |

**核心机制理解**：combine 输出直接进 residual stream，下层把它当背景噪音、不会乘性放大；dispatch 进 MoE 输入，errors 会乘性放大。

## 4. 真 EP=8 集成 + NCCL 实测

改了 `workshop/nanovllm_moe/`：
- `combine_ep_ht.py`：pack/unpack + 3-payload reverse a2a（uint8 bitcast 让 NCCL 收 int16/fp8/fp16）
- 全链路 plumbed `Config → ModelRunner → Qwen3MoeForCausalLM → ... → CombineEPHT`
- 接口：3 个 Config 字段（`moe_combine_compress_keep_frac` 等）+ env-var override

EP=8 真 NCCL 上用 4 个 prompt 验证：
- ✅ 不 crash 不 hang
- ✅ 数学题（17×23=391）在 8× 压缩下仍对
- ⚠️ wall-clock 暂时慢 1.3–1.9×（pack/unpack 在 eager 模式没融合，48 层 × 8 rank 的小 kernel 调度 overhead）

## 5. 真 task accuracy 测试（这是头号交付）

**Next-token top-1 accuracy on lcc**（4096 tokens）：

| 压缩 | PPL | top-1 acc | 掉分 | 跟 teacher 一致率 |
|---|---:|---:|---:|---:|
| teacher | 3.15 | 76.15% | - | - |
| 2× | 3.23 | 75.49% | -0.66pp | 94.84% |
| 4× | 3.70 | 72.21% | **-3.94pp** | 86.47% |
| 8× | 5.17 | 66.73% | -9.42pp | 75.78% |

**HumanEval pass@1**（164 题，真 EP=8 跑 + human-eval 测试通过率，**论文级 headline**）：

| 压缩 | **pass@1** | 掉分 (pp) | 相对掉分 |
|---|---:|---:|---:|
| teacher | **55.49%** (91/164) | - | - |
| **2×** | **47.56%** (78/164) | **-7.93pp** | -14.3% |
| **4×（甜点）** | **46.34%** (76/164) | **-9.15pp** | -16.5% |
| 8× | **18.29%** (30/164) | -37.20pp | **-67.0%（崩坏）** |

**3 个 metric 在不同档下的关系**（重要论文 finding）：

| 压缩 | PPL +% | Next-token 掉分 | HumanEval 掉分 |
|---|---:|---:|---:|
| 2× | +2.3% | -0.66pp | **-7.93pp**（12× of next-token）|
| 4× | +17.2% | -3.94pp | -9.15pp |
| 8× | +63.9% | -9.42pp | **-37.20pp**（非线性崩坏）|

**关键 take-away**：**PPL / next-token 对压缩比 task accuracy 乐观得多**——代码补全是 sequential，函数体里 ANY ONE token 错就整题挂掉。**Code 部署只看 PPL 严重低估退化**。

# 关键数字 / 真正可用的甜点

> **Frozen Qwen3-30B-A3B + combine-side 4× topk_l2 sparsification + 2× FP8 E4M3 = 8× value compression at HumanEval pass@1 -9.15pp on real 8×4090 EP=8 NCCL.**

# 阻塞与风险

1. **wall-clock 暂时慢 1.3–1.9× baseline** —— 通信省了但 pack/unpack kernel 开销吃掉了收益。这是工程优化空间不是算法死路。融合 Triton kernel + 合 buffer 单 NCCL 调用应能反超。
2. **HumanEval 是最严苛的 task** —— 自然语言任务（MMLU / 长文生成）应该掉得少得多。当前只一个 task 数字有点片面。
3. **8× 是悬崖** —— 4× 还能用、8× 就崩，希望靠"中层多保点、浅深层多压点"的不均匀压缩救回来。
